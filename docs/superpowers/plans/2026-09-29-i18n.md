# odgruz i18n Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Aplikacja i README domyślnie po angielsku; po polsku, gdy locale użytkownika to `pl` albo podano `--lang pl`.

**Architecture:** `src/i18n.ts` wykrywa język (czysta funkcja). `src/messages/` trzyma dwa ręcznie pisane słowniki o jednym typie `Messages`. Katalog celów staje się fabryką `createTargets(msgs)`, więc `Target.label`/`impact` zostają, a reszta kodu (scan, report) się nie zmienia. `clean` przestaje zwracać polski tekst: błąd strażnika ma kod `outside-roots`. Raport i CLI dostają `Messages` jako parametr.

**Tech Stack:** jak w MVP (TypeScript, vitest, tsdown). Bez bibliotek i18n.

**Spec:** prośba użytkownika z 2026-09-29: „README po angielsku, polskie w README-PL.md; apka po angielsku i po polsku, domyślnie angielski, chyba że ktoś ma locale pl”.

## Global Constraints

- Domyślny język: `en`. Polski tylko, gdy wykryte locale zaczyna się od `pl` (bez rozróżniania wielkości liter) albo `--lang pl`.
- Kolejność wykrywania: `--lang` > `LC_ALL` > `LC_MESSAGES` > `LANG` (pierwsza ustawiona, niepusta i inna niż C/POSIX/`C.*` wygrywa; C/POSIX/`C.*` są pomijane jak puste) > język macOS (`defaults read -g AppleLanguages`, pierwszy wpis) > `Intl.DateTimeFormat().resolvedOptions().locale`.
- `--lang` przyjmuje tylko `en` lub `pl`; inna wartość → komunikat w wykrytym języku, exit 1.
- Teksty polskie brzmią dokładnie jak obecnie w kodzie (nie zmieniamy tłumaczeń, tylko je przenosimy), poza poprawną odmianą liczebników.
- Raport EN nie zawiera polskich znaków; raport PL wygląda jak dziś. `<html lang="en|pl">`.
- Nazwa pliku raportu: `odgruz-report-YYYY-MM-DD-HHMM.html` (en), `odgruz-raport-YYYY-MM-DD-HHMM.html` (pl).
- Wszystkie reguły bezpieczeństwa z MVP bez zmian (guard ścieżek, brak sudo, execFile z tablicą argumentów).
- Commity kończą się `(#4)`, bez `Co-Authored-By`. Nigdy push do `main`.

## Review Focus

1. `LANG=C`/`POSIX`/`C.UTF-8` przy polskim systemie jest pomijane i decyduje następne źródło (język macOS → `Intl`), a nie wymusza `en`. Test w Task 1.
2. Pusta zmienna (`LC_ALL=""`) jest pomijana, nie wybiera `en`. Test w Task 1.
3. Raport EN bez polskich znaków (`/[ąćęłńóśźż]/i`). Test w Task 3.
4. `--lang xx` → exit 1, nic nie skanuje. Test E2E w Task 4.
5. E2E muszą ustawiać `LANG` jawnie i czyścić `LC_ALL`/`LC_MESSAGES`, inaczej wynik zależy od maszyny. Task 4.

  - `{ LANG: 'plx' }` — zaczyna się od `pl`, ale to nie kod języka: dopasowuj `^pl([_.\-@]|$)` → `en`
  - `parseLangFlag('pl')` → `pl`, `('EN')` → `en`, `('de')` → `null`, `('')` → `null`
- [ ] Implementacja:
```ts
import type { Locale } from './types.js'

const PL = /^pl([_.\-@]|$)/i
const VARS = ['LC_ALL', 'LC_MESSAGES', 'LANG'] as const

export function detectLocale(env: Record<string, string | undefined>, systemLocale: string): Locale {
  for (const name of VARS) {
    const value = env[name]
    if (value) return PL.test(value) ? 'pl' : 'en'
  }
  return PL.test(systemLocale) ? 'pl' : 'en'
}

export function parseLangFlag(value: string): Locale | null {
  const v = value.toLowerCase()
  return v === 'en' || v === 'pl' ? v : null
}

export function systemLocale(): string {
  try {
    return Intl.DateTimeFormat().resolvedOptions().locale
  } catch {
    return ''
  }
}
```
